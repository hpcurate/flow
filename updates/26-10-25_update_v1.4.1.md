## What was done

### The cause
Hugo's CORE settings have a layout, "code", with an entry for `FLOW.exe` titled **"FLOW pill"**
(x −2, y 1391, 425×64), saved while the pill was up. CORE's helper listed the pill as one of FLOW's
windows. So:
- **Opening the layout** moved the pill to that rect. The pill only called `setBounds` when its own
  rect changed (`boundsKey`), so it never noticed it had been moved, and stayed there.
- **Putting the layout away** is set to *close* for that layout: CORE sent the pill WM_CLOSE. The
  window went, while the pill's setting stayed on. That was "says it's on but it's hidden".

### FLOW (this version)
- `place()` checks the window's real bounds (±2 px), not only the last rect it set.
- A move, hide or minimise FLOW didn't make → `heal()`, 250 ms later: back in its place and shown.
  It backs off after 6 in 10 s, so it can never fight another app in a loop.
- A close FLOW didn't ask for is refused while the pill is on. Quitting FLOW still closes it
  (`before-quit`).
- Every 5 s it checks what no event reports (its window gone, hidden by another app).

### CORE 0.12.0 (the other half, logged in `core/updates/26-10-25_update_v0.12.0.md`)
- The helper skips windows that can't be activated (WS_EX_NOACTIVATE without WS_EX_APPWINDOW,
  alt-tab's own rule). The pill is one (`focusable: false`, checked on the PC: ex-style 0x08080028).
  No layout, launcher click or window list can catch it any more.
- An entry saved before ("FLOW pill" / "FLOW timer", FLOW.exe) is dropped from the layout.

### "Its own process" — Claude's call, open to change
Not done. CORE knows windows by their exe, and a second process would still be FLOW.exe, so it
wouldn't have kept CORE away by itself. The fix goes at what actually broke: CORE no longer treats the
pill as a window it can place or close, and the pill puts itself back if anything else does.
